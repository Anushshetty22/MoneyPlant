# Phase 3 Completion Checklist

Phase 3 completes the provider-aware live market path: Binance and Angel One
events are normalized into one contract, monitored independently, persisted as
latest snapshots and one-minute candles, exposed through REST and SSE, and
rendered by the same dashboard.

## Automated verification

- [x] Backend unit and integration tests pass: `go test ./...`
- [x] Backend race tests pass: `go test -race ./...`
- [x] Frontend typecheck passes: `npm run typecheck`
- [x] Frontend production build passes: `npm run build`
- [x] Binance live adapter has offline WebSocket coverage, including message
  mapping and unsafe-symbol rejection.
- [x] Angel One live adapter has offline WebSocket coverage, including the
  six-token subscription, reconnect, re-authentication, and binary decoding.
- [x] Provider-neutral integration coverage verifies that Binance and Angel One
  events reach both the latest snapshot store and one-minute candle rollup.
- [x] SSE coverage verifies snapshot, status, heartbeat, filtering, and client
  disconnect behavior.

Run the commands from the repository root unless noted otherwise:

```bash
cd backend
go test ./...
go test -race ./...

cd ../frontend
npm run typecheck
npm run build
```

## Local Angel One acceptance

These checks require the user's local PostgreSQL database, SmartAPI
credentials, an active Angel One instrument catalog, and market activity.
Never commit `.env` or any token generated by SmartAPI.

- [ ] Copy `.env.example` to `.env` and fill the four Angel One credential
  variables locally.
- [ ] Run `go run ./cmd/auth-angelone` and confirm authentication succeeds
  without printing token values.
- [ ] Refresh mappings with
  `go run ./cmd/catalog-angelone --file /path/to/OpenAPIScripMaster.json`.
- [ ] Start the API with both `LIVE_MONITOR_SYMBOLS=BTCUSDT` and
  `ANGEL_ONE_LIVE_MONITOR_SYMBOLS=TCS` configured.
- [ ] Confirm `/api/v1/live/statuses` reports the configured Binance and Angel
  One monitors as `running` after events arrive.
- [ ] Open the dashboard and verify the selected instrument chooses its
  authoritative provider source automatically.
- [ ] During market hours, verify a live BTCUSDT value and an Angel One equity
  value update in the dashboard.
- [ ] Query `/api/v1/live/stream?symbol=TCS&provider=angel_one` and observe
  `snapshot`, `status`, and `heartbeat` events.
- [ ] Stop and restart the API, then confirm `restored` is greater than zero
  and new events continue to update the snapshot.
- [ ] Query the candle endpoint after a completed minute and confirm the live
  one-minute candle is stored or updated idempotently.

## Operational expectations

- A closed market can leave a monitor healthy but show zero new events; this
  is not the same as a connection failure.
- A restored snapshot is the latest known trade, not a historical tick archive.
- Angel One `quantity` is the quantity of the latest individual trade. It is
  not the day's cumulative traded volume; the one-minute candle's `volume`
  aggregates quantities across trades in that minute.
- A stale dashboard value means no newer provider event has been received
  within the freshness window. The status endpoint remains the source of truth
  for monitor lifecycle and persistence errors.
